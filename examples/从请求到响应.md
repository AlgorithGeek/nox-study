# 从请求到响应

把一次 API 调用，整理成真正理解的知识。

学习技术时，运行成功只是一个起点。更有价值的笔记，应该能帮助我们解释：**发送了什么，收到了什么，以及下一步该检查哪里。**

这篇笔记用一个简单的 HTTP 请求，把概念、代码与复盘连起来。

## 一、先建立一张清晰的地图

一次请求可以拆成三个阶段：准备输入、发送请求、理解响应。先辨认每个部分的职责，再阅读代码，会更容易找到主线。

> **本节要点**
>
> 请求描述“我想做什么”，响应记录“服务端实际返回了什么”。不要只记住调用方法，还要记住它在整个过程中的位置。

### 请求由什么组成？

| 组成 | 示例 | 阅读时关注什么 |
| :--- | :--- | :--- |
| Method | `POST` | 用什么方法发起请求 |
| URL | `https://api.example.com/messages` | 请求发往哪个地址 |
| Header | `Content-Type: application/json` | 请求附带哪些说明 |
| Body | `{"message":"Hello"}` | 实际发送什么内容 |

这里的域名与数据仅用于说明结构。**读懂对应关系，比背下整段代码更有用。**

### 响应应该怎么看？

先看状态码，再看响应体，最后结合接口约定判断结果。

- **状态码**：提供请求处理结果的第一条线索。
- **响应头**：描述返回内容的类型等信息。
- **响应体**：包含需要进一步阅读或解析的数据。

*观察到的事实*与*对原因的推测*应分开记录。例如，“收到 401”是事实，“凭证可能有问题”是待验证的判断。

## 二、让概念落到代码里

下面是 Java 21 的请求构造示例。它只构造对象，不发送网络请求。

```java
import java.net.URI;
import java.net.http.HttpRequest;

String payload = """
        {
          "message": "Hello, Nox Study"
        }
        """;

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/messages"))
        .header("Content-Type", "application/json")
        .POST(HttpRequest.BodyPublishers.ofString(payload))
        .build();
```

阅读时，可以沿着这条路径定位：`uri()` 设置地址，`header()` 添加请求头，`POST()` 指定方法和请求体，`build()` 得到请求对象。

### 用结构化数据记录结果

下面是一份虚构的观察记录。字段名保持简单，方便以后回看。

```json
{
  "checkpoint": "first-request",
  "status": 200,
  "responseReceived": true,
  "nextStep": "read-response-body"
}
```

**记录做到哪一步，就写到哪一步。**收到响应，并不自动意味着已经理解了返回数据。

### 长代码也要保持原来的结构

链式调用通常适合分行书写；遇到日志、长地址或需要保留原貌的单行内容，可以横向滚动查看。

```java
HttpRequest request = HttpRequest.newBuilder().uri(URI.create("https://api.example.com/v1/messages?language=zh-CN&format=json&include=metadata")).header("Content-Type", "application/json").POST(HttpRequest.BodyPublishers.ofString(payload)).build();
```

短代码则只保留必要的信息：

```java
System.out.println(request.method());
```

## 三、把排查过程写成可复用的笔记

出现问题时，先保留证据，再缩小范围。不要同时修改地址、请求头和请求体，否则很难判断是哪一处影响了结果。

1. **确认输入**：方法、地址、请求头和请求体是否符合预期。
2. **记录输出**：状态码、必要的响应内容，以及发生时间。
3. **逐项验证**：每次改变一个条件，再比较前后结果。

### 一个便于回看的记录模板

| 观察到的现象 | 优先检查 | 验证方式 |
| :--- | :--- | :--- |
| 请求没有发出 | 本地配置与异常信息 | 找到失败的位置 |
| 收到认证相关错误 | 凭证是否配置、是否有效 | 按接口文档核对，避免公开真实凭证 |
| 返回内容与预期不同 | 参数与响应结构 | 对比实际输入和接口约定 |
| 修改后恢复正常 | 本次修改的具体内容 | 记录变化，再验证原先的失败场景 |

> **给未来的自己留一句解释**
>
> 不只写“修好了”，还要写“改了哪里，以及什么证据说明它修好了”。

### 学习检查点

- [x] 能指出请求方法、地址、请求头与请求体。
- [x] 能区分请求构造与实际发送。
- [ ] 能根据响应内容解释本次调用的结果。
- [ ] 能脱离示例，独立整理一次排查记录。

完成一个检查点，意味着能解释它，而不仅是看过它。

## 四、用问题完成复习

读完笔记后，合上代码，试着回答三个问题：

- 如果更换目标地址，应该查看哪一部分？
- 为什么“构造了请求对象”和“收到服务端响应”是两个不同的检查点？
- 下次出现相同问题，今天的记录能否帮助我更快找到原因？

**值得留下的重点**：把抽象概念对应到具体位置，把结论对应到观察证据。
